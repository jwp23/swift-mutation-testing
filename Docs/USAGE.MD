## Quick Start

### Generate a configuration file

```bash
# Auto-detects project type, scheme, destination, test targets, and testing framework
swift-mutation-testing init
```

This writes `.swift-mutation-testing.yml` at the project root. Review and adjust the generated file before running. For SPM packages, `scheme` and `destination` are not required and will be omitted.

### Run mutation testing

```bash
swift-mutation-testing
```

### Run an SPM package

```bash
# SPM packages are auto-detected — no scheme or destination needed
swift-mutation-testing /path/to/my-package
```

### Run on macOS without a simulator

```bash
swift-mutation-testing \
  --scheme MyScheme \
  --destination "platform=macOS"
```

### Run on iOS Simulator

```bash
swift-mutation-testing \
  --scheme MyApp \
  --destination "platform=iOS Simulator,name=iPhone 16"
```

## Configuration File

Generate a starter file with:

```bash
swift-mutation-testing init
```

### Full reference

This is the format generated by `init`. Comments show the default value for each optional field.

```yaml
# swift-mutation-testing configuration
# All settings are optional. CLI flags override file values.

scheme: MyApp
destination: platform=iOS Simulator,name=iPhone 16

# Limit test execution to a specific target (recommended when the project has UI tests)
# testTarget: MyAppTests

# Least time a mutant's tests are given, in seconds; a suite measured slower than this
# raises it (default: 120 Xcode, 30 SPM)
timeout: 60

# Number of parallel workers (default: max(1, CPU count - 1))
# concurrency: 4

# Disable result cache (re-runs all mutants on every execution)
# noCache: true

# Tests most likely to kill a mutant, for sources the Foo.swift -> FooTests.swift convention
# does not cover (SPM packages only) — see "Likely-killer tests first"
# likely-killer-tests:
#   Core/Minutes.swift: PhaseDisplayTests.swift, CountdownTests.swift

# Report output paths
# output: mutation-report.json
# htmlOutput: mutation-report.html
# sonarOutput: sonar-report.json

# Source file glob patterns to exclude from mutation
# exclude:
#   - "**/Generated/**"

# Mutation operators — set active: false to disable
mutators:
  - name: RelationalOperatorReplacement
    active: true
  - name: BooleanLiteralReplacement
    active: true
  - name: LogicalOperatorReplacement
    active: true
  - name: ArithmeticOperatorReplacement
    active: true
  - name: NegateConditional
    active: true
  - name: SwapTernary
    active: true
  - name: RemoveSideEffects
    active: true
```

### Field reference

| Field | Type | Default | Description |
|---|---|---|---|
| `scheme` | String | — | Xcode scheme to build and test (required for Xcode projects, omit for SPM) |
| `destination` | String | — | `xcodebuild` destination specifier (required for Xcode projects, omit for SPM) |
| `testTarget` | String | — | Limit test execution to this target (Xcode: `-only-testing`; SPM: see [Limiting tests to a target](#limiting-tests-to-a-target)) |
| `timeout` | Number | `120` (Xcode) / `30` (SPM) | Least time a mutant's tests are given, in seconds (see [Per-mutant timeouts](#per-mutant-timeouts)) |
| `concurrency` | Number | `max(1, CPUs − 1)` | Number of parallel test workers |
| `noCache` | Boolean | `false` | Disable result caching |
| `output` | String | — | Path for Stryker-compatible JSON report |
| `htmlOutput` | String | — | Path for interactive HTML report |
| `sonarOutput` | String | — | Path for SonarQube generic coverage report |
| `sourcesPath` | String | project root | Root directory for Swift source file discovery |
| `exclude` | List | `[]` | Glob patterns for source files to skip |
| `likely-killer-tests` | Block | — | Test files per source file for sources the `Foo.swift` → `FooTests.swift` convention misses — see [Likely-killer tests first](#likely-killer-tests-first) |
| `mutators` | Block | all active | Operator list with per-entry `active: true/false` (generated by `init`) |
| `operators` | List | all | Allowlist of operator identifiers — simpler alternative to `mutators` |

### Operator identifiers

| Identifier | What it mutates |
|---|---|
| `RelationalOperatorReplacement` | `>` `>=` `<` `<=` `==` `!=` |
| `BooleanLiteralReplacement` | `true` ↔ `false` |
| `LogicalOperatorReplacement` | `&&` ↔ `\|\|` |
| `ArithmeticOperatorReplacement` | `+` `-` `*` `/` `%` |
| `NegateConditional` | wraps conditions in `!()` |
| `SwapTernary` | swaps ternary branches |
| `RemoveSideEffects` | removes standalone function call statements |

### Operator configuration formats

There are two ways to configure operators in the YAML file.

**`mutators` block** (generated by `init`) — deny-list style. All operators are active by default; set `active: false` on entries you want to skip:

```yaml
mutators:
  - name: RelationalOperatorReplacement
    active: true
  - name: RemoveSideEffects
    active: false   # this operator will be skipped
```

**`operators` list** — allow-list style. Only the listed operators run; everything else is skipped:

```yaml
operators:
  - RelationalOperatorReplacement
  - BooleanLiteralReplacement
```

The two formats are mutually exclusive. If both are present, `operators` takes precedence. The CLI flags `--operator` and `--disable-mutator` always override the file.

## CLI Reference

### Subcommands

```bash
swift-mutation-testing [project-path] init   # generate .swift-mutation-testing.yml
swift-mutation-testing --version             # print version
swift-mutation-testing --help                # print usage summary
```

### Options

```bash
swift-mutation-testing [project-path] [options]
```

| Option | Description |
|---|---|
| `--scheme <scheme>` | Xcode scheme to build and test (required for Xcode, omit for SPM) |
| `--destination <destination>` | `xcodebuild` destination specifier (required for Xcode, omit for SPM) |
| `--target <test-target>` | Limit test execution to this target (see [Limiting tests to a target](#limiting-tests-to-a-target)) |
| `--timeout <seconds>` | Least time a mutant's tests are given (default: 120 Xcode, 30 SPM) |
| `--concurrency <n>` | Parallel workers (default: CPUs − 1) |
| `--no-cache` | Disable result caching |
| `--output <path>` | Write Stryker-compatible JSON report |
| `--html-output <path>` | Write interactive HTML report |
| `--sonar-output <path>` | Write SonarQube generic coverage report |
| `--sources-path <path>` | Root directory for source discovery |
| `--exclude <pattern>` | Exclude files matching glob pattern (repeatable) |
| `--operator <id>` | Activate only this operator (repeatable) |
| `--disable-mutator <id>` | Deactivate this operator (repeatable) |
| `--scope-lines <path:start-end>` | Test only the mutants on these source lines (repeatable, see [Scoping a run to a diff](#scoping-a-run-to-a-diff)) |
| `--since <git-ref>` | Test only the mutants the diff against this reference touches |
| `--baseline-report <path>` | JSON report of an earlier full run, so a changed test also puts the mutants it killed back in scope |
| `--quiet` | Suppress progress output |

### Limiting tests to a target

`--target` (config: `testTarget`) is interpreted differently per project type.

**Xcode projects** pass the value straight to `xcodebuild -only-testing`, so
`MyAppTests`, `MyAppTests/MyClass` and `MyAppTests/MyClass/testMethod` all work as usual.

**SPM packages** run the test bundles the single build produced, so the value is resolved against
those bundles:

- the first path component names the bundle — `MyLibTests` runs `MyLibTests.xctest` and nothing
  else;
- anything after it is passed to the bundle as an XCTest selection
  (`MyLibTests/MyClass/testMethod` runs only that test). **Known limitation:** this selection
  applies to XCTest tests only. Swift Testing tests in the same bundle all run regardless, because
  the bundle's Swift Testing entry point does not take an XCTest selector;
- if no built bundle carries that name — which is what a toolchain that merges every test target
  into one `<Package>PackageTests.xctest` produces — there is no bundle to scope the run to, and
  the run fails immediately with an error naming the target, rather than silently running every
  bundle. Running broader test scope than requested can change a mutant's kill/survive verdict
  (a test in an unrelated target may incidentally exercise the mutated code and kill a mutant the
  requested target's own tests would have missed), so a run that cannot honor `--target` refuses
  to run rather than produce a result that looks scoped but is not. Remove `--target` or
  restructure the project's test targets to get a bundle per target.

### Likely-killer tests first

A mutant is usually caught by the tests written for the file it mutates, so SPM runs those first:
`Foo.swift` is covered by `FooTests.swift`, whose test class runs as an `-XCTest` selection before
the whole suite. A failure there settles the mutant and the whole suite never runs, which is where
the time is saved. Passing those tests proves nothing — any test in the package might catch the
mutant — so the whole suite still runs before a mutant is reported as survived. `killedBy` in the
reports always names the test that actually failed, whichever of the two runs found it.

The selection is an XCTest one, so the convention only offers test files that declare an
`XCTestCase` subclass. A package tested entirely with Swift Testing selects nothing, runs its whole
suite exactly as it did before, and pays nothing for the feature.

Sources the naming convention misses need the mapping spelled out, keyed by source file path
(any path suffix, so `Minutes.swift` and `Core/Minutes.swift` both match — the longest matching
key wins):

```yaml
likely-killer-tests:
  Core/Minutes.swift: PhaseDisplayTests.swift, CountdownTests.swift
```

Names are used as written — including whether they name XCTest classes — so a typo costs nothing
but the speedup: the selection matches no test, the mutant survives a run of nothing, and the whole
suite decides as before. A source with neither
a conventional test file nor a configured entry goes straight to the whole suite. So does every
mutant when `--target` already names a class (`--target MyLibTests/MyClass`) — that selection is
the narrower one and it stands. Xcode projects always run the scope `--target` gives them.

### Scoping a run to a diff

A pull request gate does not need the whole codebase re-tested — only what the branch changed.
`--scope-lines` limits a run to the mutants on the source lines it names, and `--since` computes
that same line set from `git diff -U0 --relative <ref>`:

```bash
# Only the mutants on the lines this branch changed
swift-mutation-testing --since origin/main
```

Both flags compose with the file and operator scoping above: `--exclude`, `--operator` and
`--sources-path` still apply, and the line set narrows what is left. Files the scope does not
name are never parsed, so a scoped run is cheaper than a full one at every stage — discovery,
build and test.

**A changed test file puts mutants in scope too.** A test file carries no mutants, so a run scoped
to the diff alone would pass a test-only change without testing anything. Every test file in the
scope therefore also puts in scope:

- every mutant of the source it covers — `FooTests.swift` covers `Foo.swift` by the same naming
  convention [Likely-killer tests first](#likely-killer-tests-first) uses, and the same
  `likely-killer-tests` mapping overrides it;
- every mutant `--baseline-report` records that test as having killed, wherever that mutant lives.
  A test kills mutants in files the convention never pairs it with, and weakening it should be
  caught. The report is the JSON `--output` wrote on an earlier full run; the tool reads the path
  it is given and never goes looking for one.

A deleted test file counts as changed: it has no lines left, but the source it covered goes back in
scope whole.

`--baseline-report` only widens a scope `--scope-lines` or `--since` already narrowed, so it
requires one of them — given alone, it has nothing to widen and the run would test every mutant
regardless.

```bash
# PR gate: the branch's own changes, judged also against what its tests used to kill
swift-mutation-testing --since origin/main --baseline-report main-report.json
```

A scoped run that holds no mutant at all prints `No mutants in scope. Nothing to test.`, the scope
it resolved, and exits `0` without building. A change that touches no mutable line passes; it does
not fail and it does not silently score itself over nothing. The scope is printed so that a
mistyped `--scope-lines` path is visible rather than passing as a green gate forever:

```
No mutants in scope. Nothing to test.
Scope: Sources/Foo.swift:10-20, Tests/FooTests.swift:all
```

Any report `--output`, `--html-output` or `--sonar-output` asked for is still written, holding no
mutants, so CI steps that expect the file to exist after every run still find it.
### Per-mutant timeouts

Before any mutant runs, an SPM package's test suite runs once unmutated, in the built sandbox, the
same way a mutant's tests run. That baseline does two things.

It checks the suite passes to begin with. A suite that already fails would fail again under every
mutant and report every one of them killed, so a failing baseline ends the run instead, naming the
tests to fix:

```
The test suite fails before any mutation is applied, so every mutant would be reported killed by a
failure that is already there. Fix these tests first:
  - MyLibTests.ParserTests.testTrailingComma
```

It also times the suite, and each mutant's timeout is set from what the tests it runs took
unmutated — five times that, or `--timeout`, whichever is longer. `--timeout` is therefore the
*least* time a mutant gets, never a cap: a suite slower than it raises the timeout to match, so a
slow suite stops reporting honest survivors as timeouts, and no project that runs today starts
timing out because of the measurement. A mutation can legitimately make code slower than any
multiple of a fast suite — a loop that runs longer, a cache that stops hitting — and `--timeout` is
the patience you keep for that.

The baseline run itself is allowed five times `--timeout` — how long the suite takes is the very
thing it exists to find out, so holding it to the per-mutant floor would end the run on exactly the
slow suites the measurement is for. A suite slower even than that ends the run asking for a higher
`--timeout`.

Xcode projects run no baseline: their tests are selected through an xctestrun plist rather than by
running bundles, so `--timeout` is used exactly as given.

### Common invocations

```bash
# Run with config file (no extra flags needed)
swift-mutation-testing

# Override scheme and destination
swift-mutation-testing --scheme MyApp --destination "platform=macOS"

# Limit to a single test target
swift-mutation-testing --target MyAppTests

# Run only two operators
swift-mutation-testing \
  --operator RelationalOperatorReplacement \
  --operator BooleanLiteralReplacement

# Disable one operator, keep the rest
swift-mutation-testing --disable-mutator RemoveSideEffects

# Exclude generated code
swift-mutation-testing --exclude "Sources/Generated/**"

# Generate all report formats
swift-mutation-testing \
  --output mutation-report.json \
  --html-output mutation-report.html \
  --sonar-output sonar.json

# Suppress progress output (useful in CI)
swift-mutation-testing --quiet

# Invalidate cache and run fresh
swift-mutation-testing --no-cache
```

## Output Formats

### Progress output (default)

Streams build events and per-mutant results to stdout during execution.

```
  ✓ Discovery: 147 mutants (143 schematizable, 4 incompatible) in 2.3s

Building for testing...
  ✓ Built in 18.4s
  ✓ 3 simulators ready

Testing mutants...
  ✓ 1/147  ArithmeticOperatorReplacement  Calculator.swift:12
  ✗ 2/147  RelationalOperatorReplacement  Validator.swift:34
  ⚠ 3/147  RemoveSideEffects              Service.swift:55
  ⏱ 4/147  NegateConditional              Loop.swift:9
```

**Progress icons:**

| Icon | Meaning |
|---|---|
| `✓` | Killed — tests detected the mutation |
| `✗` | Survived — tests passed with the mutation active |
| `⚠` | Unviable — mutant did not compile |
| `⏱` | Timeout — test process exceeded the timeout |
| `–` | No coverage — no test reached the mutated code |

### Text summary (always printed)

```
Results by file:
  Sources/Calculator.swift    score: 95.0%   killed: 19   survived: 1   timeout: 0   unviable: 0
  Sources/Validator.swift     score: 72.4%   killed: 21   survived: 8   timeout: 0   unviable: 0

Survived mutants:
  Sources/Validator.swift:34:5   RelationalOperatorReplacement
  Sources/Validator.swift:67:12  NegateConditional

Overall mutation score: 83.2%
Killed: 122 / Survived: 21 / Timeouts: 0 / Unviable: 4 / NoCoverage: 0
Total duration: 312.7s
```

**Mutation score formula:**

```
score = killed / (killed + survived + timeouts + noCoverage) × 100
```

Unviable mutants are excluded from both numerator and denominator.

### Quiet mode (`--quiet`)

Suppresses all progress output. Only the text summary is printed at the end.

### JSON report (`--output`)

Stryker-compatible JSON report written to the specified path. Includes per-file source content, per-mutant status, and score thresholds.

```bash
swift-mutation-testing --output mutation-report.json
```

### HTML report (`--html-output`)

Interactive per-file dashboard with colour-coded scores and inline survived mutant details.

```bash
swift-mutation-testing --html-output mutation-report.html
```

### SonarQube report (`--sonar-output`)

SonarQube Generic Issue Import Format. Survived mutants are reported as `MAJOR CODE_SMELL` issues; no-coverage mutants as `MINOR`.

```bash
swift-mutation-testing --sonar-output sonar.json
```

### Caching

Results are cached at `<project>/.swift-mutation-testing-cache/results.json`, keyed by SHA256 of the source and test file contents. On subsequent runs, cached mutants skip the build and test cycle entirely.

```
  ✓ Loaded 147 mutants from cache
```

Use `--no-cache` to force a full re-run:

```bash
swift-mutation-testing --no-cache
```

## Suppressing Mutations

Apply the `@SwiftMutationTestingDisabled` attribute to any function, type, or property to exclude all mutations within that scope.

```swift
@SwiftMutationTestingDisabled
func legacyParser(_ input: String) -> Result {
    // All mutations inside this function are suppressed
}

@SwiftMutationTestingDisabled
struct GeneratedModel {
    // All mutations inside this type are suppressed
}
```

**Supported scopes:** functions, initializers, classes, structs, enums, extensions, stored properties.

Suppressed mutations never appear in the report — they are filtered out before execution.

## CI/CD Integration

### GitHub Actions — run on every push

```yaml
- name: Mutation testing
  run: |
    swift-mutation-testing ${{ github.workspace }} \
      --scheme MyApp \
      --destination "platform=macOS" \
      --quiet
```

### GitHub Actions — generate HTML report as artifact

```yaml
- name: Mutation testing
  run: |
    swift-mutation-testing ${{ github.workspace }} \
      --scheme MyApp \
      --destination "platform=macOS" \
      --html-output mutation-report.html \
      --quiet

- name: Upload mutation report
  uses: actions/upload-artifact@v4
  with:
    name: mutation-report
    path: mutation-report.html
```

### GitHub Actions — SonarQube integration

```yaml
- name: Mutation testing
  run: |
    swift-mutation-testing ${{ github.workspace }} \
      --scheme MyApp \
      --destination "platform=macOS" \
      --sonar-output sonar.json \
      --quiet

- name: SonarQube scan
  uses: SonarSource/sonarqube-scan-action@v2
  with:
    args: >
      -Dsonar.externalIssuesReportPaths=sonar.json
```

### GitHub Actions — with config file

```yaml
- name: Mutation testing
  run: swift-mutation-testing ${{ github.workspace }} --quiet
```

When `.swift-mutation-testing.yml` is committed to the repository, no additional flags are needed.

### Speed up CI with caching

Cache the `.swift-mutation-testing-cache` directory between runs to avoid re-testing unchanged mutants.

```yaml
- name: Cache mutation results
  uses: actions/cache@v4
  with:
    path: .swift-mutation-testing-cache
    key: mutation-cache-${{ hashFiles('Sources/**/*.swift', 'Tests/**/*.swift') }}
    restore-keys: mutation-cache-

- name: Mutation testing
  run: swift-mutation-testing ${{ github.workspace }} --quiet
```

### Limit scope in CI

Run only a subset of operators to keep CI fast, and run the full suite locally:

```yaml
- name: Mutation testing (fast)
  run: |
    swift-mutation-testing ${{ github.workspace }} \
      --operator RelationalOperatorReplacement \
      --operator BooleanLiteralReplacement \
      --quiet
```

## Exit Codes

| Code | Meaning |
|---|---|
| `0` | Success |
| `1` | Error — usage error, build failure, or unexpected failure |

Use the exit code in shell scripts:

```bash
swift-mutation-testing --quiet
case $? in
  0) echo "Mutation testing completed" ;;
  1) echo "Error — check scheme, destination, and project path" ; exit 1 ;;
esac
```
